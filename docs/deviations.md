# Deliberate deviations

Where dotcl knowingly behaves differently from the standard, or from SBCL. Each
row was decided rather than discovered: if you find something not listed here
that differs, it is a bug and worth reporting.

Two kinds of entry appear. Some rows differ from a strict reading of the
standard in order to agree with the implementations that real libraries are
written against. Others differ from SBCL, because the standard leaves the point
open and dotcl reads it differently.

| Area | dotcl | CLHS / SBCL | Why | State |
| --- | --- | --- | --- | --- |
| `defgeneric` over a name that already has an ordinary function | Warns, removes the function definition, and defines the generic function | CLHS 7.6.1 says an error is signaled; SBCL warns and then signals a `program-error` as well, and its ordinary function stays in place | Widely used libraries (cl-ppcre among them) reach this case while loading, and erroring stops them dead | permanent |
| Floating-point exceptions | One rule. In code compiled at `(safety 3)`, a float operation whose operands are finite and not NaN signals when its value is not: `floating-point-overflow` for a result too large for its format, `division-by-zero` for a quotient by zero, `floating-point-invalid-operation` for a NaN (`(/ 0.0 0.0)`, `(- inf inf)`, `(sin inf)`), each with the operation and operands. This covers `+ - * /` declared or not, `coerce`, `float`, `scale-float`, `exp`, `expt`, `log` (of zero: `division-by-zero`), `sin`, `cos`, `tan`, `sinh` and `cosh`. At `(safety 0)` to `(safety 2)`, the default included, in the interpreter, and through `funcall` or `apply` of `#'+` and the like even from `(safety 3)` code, the value is the IEEE infinity or NaN. At every safety an infinite or NaN operand propagates (a comparison with a NaN operand answers false, `/=` true, where SBCL signals `floating-point-invalid-operation`), underflow flushes to zero, and the operations with no float value to return signal: the conversion of an integer or ratio too large for the float format (`float`, `coerce`, mixed arithmetic, `expt`, and the transcendental functions, which take a rational as a single-float, `sqrt` and `expt` as a double-float: `floating-point-overflow`), rational division by zero, including `expt` of a rational zero to a negative rational power, and `floor` / `truncate` / `mod` / `rem` and their float variants by zero (`division-by-zero`) | CLHS 12.1.4.3 says overflow and division by zero should be signalled; by 1.4.2 that requires a signal only in safe code, compiled at the highest safety. It permits flushing underflow to zero. SBCL traps in hardware and signals at every safety, and flushes underflow | .NET has no floating-point trap, so a signal costs a test on every result: 5-120% on declared float loops at `(safety 1)` (Coalton compiles its standard library at `(safety 1)`). Safe code pays it; other code keeps the speed. Underflow is not signalled: the trap is masked by default on every host dotcl runs on, as it is in SBCL, CCL and ECL | permanent |
| Arithmetic `loop` variable seen by `finally` | The value after the final step: `(loop for x from 1 to 5 do (progn) finally (return x))` is 6 | The conformance suite expects the last in-body value; CLHS 6.1.2.1.1 does not settle it, and the suite tags those tests as a spec problem itself. SBCL and ABCL return the stepped value | Libraries are written against what the implementations do -- babel's unibyte encoders read the stepped value | permanent |
| `make-array` of element type `t` with no `:initial-element` | Every element is `nil`: `(make-array 3)` is `#(nil nil nil)`, adjustable and displaced-free vectors and arrays of higher rank included | CLHS 15.1.2.2 leaves the initial contents undefined. SBCL fills with `0` | A `nil` is the one value that is safe to find in a vector of type `t` and that a missing store shows up as at once. Code that reads an element it never stored depends on SBCL's zero fill: quantile-estimator sorts a 512-element buffer of which only the first entries are set, and `(sort buffer #'>)` meets `nil` | permanent |
| Printing a circular list with `*print-circle*` nil | Stops and prints `...`. The cut is found inside the cycle rather than at its entry, so a few more elements are printed than a per-cons table would emit. With `*print-readably*` true it prints the same `...`, where the CLHS description of `*print-readably*` asks for `print-not-readable` (SBCL loops instead) | The standard leaves printing circular structure without `*print-circle*` undefined | Terminating beats printing forever, and the two-pointer guard that finds the cycle costs no allocation, so ordinary list printing does not pay for it | permanent |
| Printing infinities and NaN | `#.DOTCL:DOUBLE-FLOAT-POSITIVE-INFINITY` and friends, which read back; with `*read-eval*` nil, an unreadable `#<...>` form; with `*print-readably*` also true, `print-not-readable` | The standard gives these no external representation; SBCL prints an infinity as a constant from its own package and a NaN as `#<DOUBLE-FLOAT quiet NaN>`, which does not read back | The printed form has to read back whatever `*package*` is, and an unqualified name does not: dotcl's `CL-USER` does not use `DOTCL` | permanent |
| `~E` with an explicit digit count | Rounds the exact binary value | SBCL rounds the shortest representation that reads back, then pads with zeros | The conformance suite checks `~E` output against the rational the float denotes, so the exact value is what passes there. `~F` follows SBCL except for subnormal numbers, which it prints digit for digit from the binary value: `(format nil "~f" least-positive-double-float)` ends in `5` after 325 characters, SBCL's ends in `49406564584124654`. `prin1` of the same number differs too (`5.0d-324`, SBCL `4.9406564584124654d-324`); both read back to the same value | permanent |
| `open :direction :output :if-exists :append`: moving the position | Every write goes to the end of the file as it is at that moment, so another appender's data is never overwritten. `file-position` reports that end; setting it to anything else returns `nil` | SBCL opens with `O_APPEND` too, but setting the position returns `t` and the next write still goes to the end; its `file-position` also keeps the value it had when another appender has since written (10 where dotcl says 12) | Answering `t` would promise a write position that the OS does not honour. The end-of-file guarantee comes from the OS: an append-only handle on Windows, `O_APPEND` on Linux and macOS. Elsewhere (other Unix systems, WebAssembly) the stream seeks to the end once, at open, which is right only while it is the sole writer. `:direction :io` with `:if-exists :append` also still seeks once | until a caller needs the other answer |
| `open :direction :output` on an existing file with no `:if-exists` | The existing file is replaced (`:new-version`, which on a file system without versions behaves as `:supersede`) | SBCL on Unix signals a `file-error` (`:error`) | CLHS makes the default `:new-version` when the pathname version is `:newest` and `:error` otherwise. A namestring with no version has the version `:newest` (as in SBCL, CCL and ECL), so the standard's default is `:new-version`; SBCL takes the `:error` branch that an implementation without versions is allowed to take. dotcl follows the default the standard gives for a `:newest` version | until a caller needs the other answer |
| `~wF` with a width that is too short and no scale factor | The zero after a final point stays when it takes the last column, and a value that rounds to no integer digit with no column to spare prints `.0`: `(format nil "~2f" 1.0)` is `1.0`, `(format nil "~3@F" 1.0)` is `+1.0`, `(format nil "~1f" 0.01)` is `.0` | SBCL drops the zero (`1.`, `+1.`) and prints the digits as they are (`.01`) | The conformance suite (FORMAT.F.5, FORMAT.F.8, FORMAT.F.45, FORMAT.F.46) expects the first form; with a scale factor given (`~3,,2F`), dotcl prints what SBCL prints | permanent |
| `~G` with an explicit digit count on a single-float, and the exponent after a carry | `(format nil "~,10g" 1.5e12)` gives `1.5000000266e+12` (the exact single-float value); `(format nil "~,3g" 9999999.0)` gives `1.000e+7`; default `~G` of a subnormal is the full binary expansion | SBCL gives `1.5000000000e+12` (the shortest form that reads back, padded with zeros), `10.000e+6`, and a form cut at about 17 digits | CLHS 22.3.3.3 decides none of the three, and dotcl's own format tests already record the direction of an exact tie as free. The default `~G` of an ordinary value, and ties such as `(format nil "~,3g" 1234.5)` (`1.235e+3`), agree with SBCL | until a caller needs one |
| A call, in a file compiled with `compile-file`, to a small function defined earlier in the same file | The function's body is substituted at the call, without an `inline` declaration, behind a check that the name still holds that function; so a later redefinition, `trace` or `(setf fdefinition)` still takes effect. The substituted function has no frame of its own in a backtrace. `notinline`, or `(debug 3)` at the definition or the call, keeps the call | CLHS 3.2.2.3 permits it; SBCL substitutes only functions declared `inline` | The call costs more than a small body on .NET | permanent |
| `subtypep` with `real` against `(or rational float)` | `(subtypep 'real '(or rational float))` is `nil t`: `dotcl:decimal` is a third kind of real, neither rational nor float (see numbers.md) | SBCL answers `t t` | The answer has to agree with `typep`: `#m0.5` is a real in no member of the union, and a `t t` would let the compiler drop a case it can reach | permanent |
| Loading the same fasl, or the same system, again in one process | The first load of a fasl path runs as the file's own .NET assembly and may use its native (ReadyToRun) code. Every later load of that path reads the file as IL into a collectible load context, so the replaced definitions' assembly is unloaded by a garbage collection once nothing refers to its functions or classes: a `load-system` / `clear-system` cycle no longer grows the process (500 loads of a file with structures, classes, methods and closures left 31 assemblies where 530 used to stay). A function kept from an old load keeps that load's assembly alive. Still not unloaded: the assembly of each path's first load, the classes `defclass` makes for .NET interop, and the FFI callback assembly | SBCL frees a replaced definition when nothing refers to it | An assembly in a collectible context cannot run precompiled code, so a reload is JIT-compiled (a load from bytes always was); the first load keeps the native-code speed. Unloading happens at a garbage collection, so `(gc)` shows it sooner | by design; a path loaded again never goes back to native code |
| `setq` / `incf` of a captured variable that is declared `fixnum` or `double-float` | The assigned value is not checked against the declaration: `(let ((d 0d0)) (declare (double-float d)) (funcall (lambda () (setq d 1))) d)` returns `1`, and an `incf` of a captured `fixnum` can pass the fixnum range. The same assignment in the binding's own body signals `type-error`, because the variable lives in a native slot there | SBCL signals `type-error` in both places | A declaration that the program breaks leaves its meaning undefined (CLHS 3.3.4), and the variable of a closure is a boxed cell that carries no type, so a check would need the declaration carried into every capturing lambda | until a caller needs the other answer |
| `dotimes` with a count that is not an integer | The loop runs for the ceiling of a real count: `(dotimes (i 2.5) ...)` runs 3 times | SBCL signals a `type-error`; the standard asks for an integer | The ceiling is what the old `(>= counter count)` test did, and the loop test stays one integer compare | until a caller needs the other answer |
| `:start` given as `nil` to string and sequence functions | `nil` is taken as `0` by some of them: `(string-upcase "abc" :start nil)`, and `string-downcase`, `string-capitalize`, `nstring-upcase`, `position`, `find`, `count`, `remove`, `delete`, `substitute`, `nsubstitute`, `remove-duplicates` and `read-from-string`. The others signal a `type-error` for it, as SBCL does: `fill`, `replace`, `search`, `mismatch`, `reduce`, `string=` and the other string comparisons, `remove-if` and the other `-if` functions, `write-string`, `write-line`, `parse-integer`, `with-input-from-string`, `make-string-input-stream` and `subseq`. `:end nil` means the end of the sequence in all of them, as the standard says | SBCL signals a `type-error` for a `nil` `:start` in every one of them; CLHS says `:start` is a bounding index, which `nil` is not | Libraries pass `nil` through from optional arguments, and rejecting it would stop them where the answer is obvious | permanent |
| `use-package` of the `keyword` package; a macro lambda list with `&rest` and no variable | Accepted: `(use-package :keyword pkg)` succeeds and `(defmacro m (a &rest) ...)` is read as having no rest variable. `unintern` given a string signals a `type-error`, as in SBCL | SBCL signals a package-lock error for the first and a lambda-list error for the second | Sloppy code that works elsewhere keeps working, and neither changes what a correct program does | until a caller needs the other answer |
| `schar` (or `svref`) given an array that is not simple: an adjustable or fill-pointer string | The element is read: `(schar (make-array 3 :element-type 'character :adjustable t :initial-element #\\a) 0)` is `#\\a` | SBCL signals a `type-error`; the standard says the argument is a simple string | Compiled `schar` is a direct element read with a fallback for the other string kinds, and a simplicity test would be added to a hot path to refuse an argument that is read correctly; nothing wrong is returned | permanent |
| `svref` given an object that is not a simple vector, such as a string | The element is read: `(svref "abc" 0)` is `#\\a`, and `(svref (make-array 3 :adjustable t :initial-element 7) 0)` is `7` | SBCL signals a `type-error`; the standard says the argument is a simple vector | Compiled `svref` is a direct element read, and a type test on every call made it 8 to 10 percent slower in a measurement; a program that passes a correct simple vector is unaffected, and nothing wrong is returned for the other kinds | until a caller needs the other answer |
| `make-condition` / `error` with `:format-arguments` that do not fit the control string | The condition is made. Printing a `make-condition` one falls back to a generic line (`Condition SIMPLE-ERROR was signalled.`); an `error` called with a string prints the control string as it is | SBCL signals a `format` error when the condition is printed | A failing report would hide the original error | permanent |
| A printer variable or option bound to an invalid value: `*print-case*` not `:upcase` / `:downcase` / `:capitalize`, `*read-default-float-format*` not a float format, `make-string-output-stream :element-type` not a character type, an invalid `:pprint-dispatch` | The binding is accepted and printing falls back to the default behaviour; `write` itself checks `:base`, `:case`, `:level`, `:length`, `:lines`, `:miser-width` and `:right-margin` | SBCL signals a `type-error` when the value is used | The value only matters where it is used, and checking an assignment would blur the line with code that binds a variable temporarily; nothing wrong is returned | until a caller needs the other answer |
| `*macroexpand-hook*` during `compile`, `compile-file` and `eval` | The hook is called for each macro call the compiler expands (a user macro; its result is the expansion) and, as a notification only, for each standard macro the compiler lowers itself (`defun`, `when`, ...): the function it is given returns the form unchanged, so a hook that rewrites the expansion of a standard macro has no effect. The hook sees only these call forms, not the macros SBCL's own `lambda` / `defun` expansions use inside, a nested form can be seen more than once per compile, and its third argument is `nil` | SBCL calls it for every macro it expands, including those internal ones, once each, with an environment object as the third argument, and a hook that returns a constant for a standard macro changes the expansion (a `type-error` in the usual case) | Libraries that collect definitions through the hook (docparser) only need the call forms; reproducing SBCL's internal macros would mean expanding standard macros that the compiler lowers directly | until a program needs the exact sequence |
| `~&` at the start of a pretty logical block (`~<` ... `~:>`) | Prints no newline when the column is 0, as CLHS 22.3.1.3 specifies. | SBCL prints one extra newline there (`(format nil "~<~&x~:>" nil)` is "x" here, a newline then "x" in SBCL; the same after a `~%` or `~:@_` in the block). | The standard says `~&` prints a newline only if the column is not 0. | permanent |
| Titlecase characters such as U+01C5 | They have no case in `char-upcase` / `char-downcase` / `both-case-p`; `string-equal` and `equalp` do not equate them with their upper or lower forms | SBCL maps them | CLHS 13.1.4.3 requires a one-to-one mapping between the upper and lower case of a character with case, and a titlecase character has two counterparts | permanent |
| `char-code-limit` and characters outside the Basic Multilingual Plane | `char-code-limit` is 65536: strings are UTF-16, `(code-char #x1F600)` is `nil`, and a character above `#xFFFF` read from a file is two characters (a surrogate pair) | SBCL: `char-code-limit` is 1114112 and such a character is one character | dotcl keeps .NET's `string` and `char` as its own, so text crosses to and from .NET without conversion; raising the limit was decided against. Libraries that assume a code point is one character need a `#+dotcl` branch that keeps the pair, or skips the code point | decided |

## Library backends

**CFFI foreign pointers are plain integers.** The CFFI-SYS backend that the
dotcl dist ships represents a foreign pointer as the integer address itself:
`null-pointer` is `0`, `inc-pointer` is `+`, and `foreign-pointer` is the type
`integer`. So `pointerp` is true of every integer, including `42` and `0`, and
`pointer-eq` and `null-pointer-p` accept any integer without signalling. On
SBCL a pointer is a separate object (a SAP) and all three reject a bare
integer. Four tests in CFFI's own suite check exactly that and fail on dotcl:
`POINTERP.4`, `POINTERP.5`, `POINTER-EQ.NON-POINTERS.1` and
`NULL-POINTER-P.NON-POINTER.2`. The integer form is what .NET interop hands
over and accepts for an address (`IntPtr` converts to and from an integer), so
every pointer crosses that boundary without a wrapper being allocated or
unwrapped, and pointer arithmetic stays integer arithmetic. CFFI's Allegro
backend makes the same choice for the null pointer, which is also the integer
`0` there. A distinct pointer type would change every path through `mem-ref`,
`inc-pointer` and the callbacks, and any existing code that passes an address
it got from .NET straight to CFFI; it is not planned until a library needs to
tell a pointer from an integer.

Behaviour at the boundary between Lisp and .NET -- which exception is caught
where, and what a condition escaping a callback does -- is a larger topic with
its own table in [DESIGN.md](../DESIGN.md), section 3.11.

## Where the conformance suite is adjusted

dotcl runs the ansi-test suite unmodified, from a fresh clone. Five
adjustments are made in the harness instead, and they follow from the table
above:

- **Eight `EXP.ERROR` / `EXPT.ERROR` tests are skipped**, through the note the
  suite already carries for implementations that do not signal underflow by
  default. SBCL and the others skip them the same way.
- **Five `LOOP.1` tests (`LOOP.1.39` to `LOOP.1.43`) are skipped**, through a note registered for them,
  because they ask the question the standard leaves open above. The suite tags
  them as a spec problem itself; disabling the narrow note rather than that tag
  keeps unrelated tests running.
- **Eight printer tests get their random range narrowed by a single value.**
  `PRINT.{SHORT,SINGLE,DOUBLE,LONG}-FLOAT.{2,4}` each draw integers from a
  range whose low endpoint is exactly the magnitude at which CLHS
  22.1.3.1.3 stops using fixed-point notation, so at that one draw the
  tests' expectation is out of spec -- dotcl, SBCL and ABCL all print it in
  exponential notation. The remaining draws still run, and the override
  checks that the upstream test still carries the draw it was written with,
  so a change upstream is reported rather than silently shadowed.
- **Two `ENCODE-UNIVERSAL-TIME` tests get their 1900 guard corrected.**
  `ENCODE-UNIVERSAL-TIME.{1,3}` draw dates from 1900 on with zones from -24
  to 24 hours, and keep the zone non-negative on 1900-01-01 so the result
  stays a universal time, but the guard tests for date 0 of month 0, which
  never occurs. An early hour of 1900-01-01 with an eastern zone then asks
  for a negative universal time, which dotcl and SBCL both reject with a
  `type-error`; the harness tests for January 1 instead. The override checks
  the upstream guard the same way as the printer tests.
- **One `COMPILE-FILE` test is run without the harness muffling its
  style-warnings.** It checks that a style-warning makes `COMPILE-FILE` return
  a true warnings-p, while the harness muffles every style-warning around a
  test, and a warning muffled outside `COMPILE-FILE` is not counted (SBCL
  answers the same way). The test gets the suite's own
  `:do-not-muffle-warnings` note, so it sees the warning as written.

Everything else in the suite is expected to pass; the current count and the one
known failure live in `ansi-state.json`.
