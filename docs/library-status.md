first. Generated by `bench/library-status/render.lisp` -- do not
edit this file by hand.

Order is how many other Quicklisp projects are built on a
project, directly or through others, not counting dependencies
of test systems or projects with the same owner.
Every project with at least 4 is a row.
One row per release: a library and its test system are one
thing to install and one row here. See
`bench/library-status/README.md` (stage 1) for the exact rules.

| status | meaning |
| --- | --- |
| `ok` | loads, and the library's own test suite ran here and passed |
| `load-only` | loads; its test suite was not run here, or did not pass (the tests column says which) |
| `patched` | loads from the patched release in the dotcl dist overlay |
| `fail` | does not load |
| `not checked` | not measured in this run |

The tests column is what running the library's own test suite
(`asdf:test-system`) printed, read by a recogniser for the test
framework (fiveam, rt, rove, prove, parachute, stefil, fiasco,
clunit, Try, 1am, lisp-unit, lisp-unit2, lift, ptester, unit-test,
should-test, and the harnesses of cl-ppcre and flexi-streams,
counted per suite).

| tests | meaning |
| --- | --- |
| <framework>: N passed | the suite ran and every check passed (the row is ok) |
| <framework>: K of N failed | the suite ran and K checks failed |
| <framework>: error after N passed | the suite started, then signalled or exited abnormally |
| ran; no recognised result | the test operation finished but printed no summary a recogniser knows; not a pass |
| error | the test operation signalled before any recognised summary |
| timeout | the test run hit its time bound |
| test system did not load | the library loads but its test system does not |
| (blank) | the suite has not been run |

Some libraries have a dotcl fork with the fix that the dotcl dist
does not carry yet. The with forks column is filled for a row that
is not ok and whose dependencies reach such a fork: the same row
measured again with those forks ahead of the dists. It names the
forks reached and what the run saw. It never changes the status,
which is what the dists give you today.

| with forks | meaning |
| --- | --- |
| pending-fork (F): ... | loads, or passes, only with the forks F: the row waits on a fork reaching the dotcl dist |
| improved (F): ... | better with the forks F (fewer failures, or an error that became a failure), but still not ok |
| same (F): ... | no better with the forks F: they are not what the row waits on |
| worse (F): ... | worse with the forks F |
| (blank) | not measured with forks: the row is ok, or reaches no fork |

The seconds column is the wall-clock time of the process that
loaded the row, and of the one that ran its test suite, on dotcl
and on SBCL from the same dists. Both measure the rows in this
order from an empty compile cache, so a row's time includes
compiling the dependencies it is the first to need. dotcl's
times include its start-up, about a second per process.
